# Banking OS Alignment Audit — Knowledge Tree (`knowledge/**`)

**Scope:** ~122 markdown files under `knowledge/`, **excluding** the two standards themselves (`knowledge/product/banking-os.md`, `knowledge/design-system/narrative-spine.md`) and the rest of `knowledge/product/`. Prioritised narrative / positioning / value-shaping knowledge: value frameworks, value propositions, messaging, methodology, domains, benchmarks, platform/Backbase capability descriptions — the content that feeds the agents.
**Judged against:** `knowledge/product/banking-os.md` (Banking OS = control plane · Nexus + Sentinel · 2 domains → 4 solutions · Conversational Banking Assist/Transact/Resolve/Grow · Resolution Loops · Factory/Missions · three value pools · value-leakage / resolution-loop method) and `knowledge/design-system/narrative-spine.md` (From→To voice, retired vocabulary).
**Date:** 2026-06-09 · **Auditor:** Banking OS Alignment Checker (read-only).

## Headline finding

The knowledge tree is **split-brain**. The newest modules (added through Mar–Jun 2026) are **fully aligned** to the Banking OS — the **APA Domain Matrix** (`knowledge/domains/apa-matrix/`) and the **Field CDO job description** both name Sentinel/NEXUS/Intelligence Fabric, the 6-layer Banking OS, and the "engagement banking → AI-native Banking OS" pivot explicitly. But the **foundational reference layer that the pipeline agents actually read is one product generation behind**: `backbase_platform_lexicon.md` (the "authoritative source" the agents cite) and the entire **Ignite Inspire** knowledge pack still describe Backbase as the **"Engagement Banking Platform" / 6-product suite**, on a **three-fabric / three-plane** architecture, with **Sentinel absent entirely** and NEXUS framed only as a semantic fabric (HELIX successor) rather than as a layer of the control plane paired with Sentinel.

Because the agents source product terminology and value framing from the *stale* foundational files — not from the aligned new modules — the old story propagates by default. The aligned content (APA matrix, Field CDO docs) is excellent but **siloed**: nothing routes the agents to it as the canonical product model.

**Three patterns recur:**
1. **Stale positioning** — "engagement banking platform", "digital experience", "omnichannel", "customer experience orchestration" as lead framing (lexicon, competitor intel, Ignite pack, MCP integration).
2. **Outdated architecture** — three-fabric / three-plane / 13-product-lines / lifecycle-quadrants model; NEXUS-without-Sentinel; no control-plane, no 4 Solutions, no Conversational Banking solution, no Resolution Loops (lexicon, Ignite agent-4, agent-6).
3. **Value-method drift** — value framed by the Acquire/Activate/Expand/Retain lifecycle flywheel rather than the **three value pools** + **value-leakage / resolution-loop** method; benchmark/ROI envelopes that don't reconcile to banking-os.md's $150–300M / three-pool model (value_lever_framework, capability_driven_patterns, backbase_platform_lexicon §6, roi_examples).

## Cascade recommendation

The single highest-leverage fix is **`knowledge/backbase_platform_lexicon.md`**. It declares itself the authoritative product source and is the file the pipeline agents read for terminology and architecture — so every stale frame in it (Engagement Banking Platform, three-fabric/three-plane, 13 product lines, lifecycle quadrants, NEXUS-without-Sentinel, no 4 Solutions, no Resolution Loops) cascades silently into discovery synthesis, capability assessments, journey maps, use-case design, and readout decks. Fixing the lexicon — re-basing it on `banking-os.md` and demoting the old architecture to a clearly-labelled "superseded" appendix — corrects the largest number of downstream agents at once. The **Ignite Inspire pack** is the second cascade point: it is a self-contained world that re-teaches the Engagement-Banking-Platform / omnichannel / 3-plane model in five+ files, and it has no pointer to the canonical sources; a one-time pack-level canonical-source banner plus a shared Banking OS preamble would arrest most of that drift cheaply.

Two structural moves make the fix durable rather than cosmetic: (1) add a standing instruction across the knowledge tree (and ideally enforced in the agents) that **`banking-os.md` is product substance and `narrative-spine.md` is voice** — read both first, treat the lexicon/Ignite content as legacy until rebased; and (2) **route AI/value/use-case work to the already-aligned APA matrix** as the default lens, so the good new model actively displaces the stale one instead of sitting in a silo. Do not rewrite the methodologically-sound assets wholesale (value_lever_framework's four-link chain, the ROI worked examples, the competitor *facts*) — re-frame their *positioning and value taxonomy* onto the control plane and three pools, and keep the rigor.

## APA matrix ↔ resolution-loop relationship (explicit note)

**They are the same method under two names — complementary, lightly overlapping, not contradictory.**

- `banking-os.md` §9 defines the **Value-Leakage / Customer-Resolution-Loop method**: find broken customer-intent loops where **time · contact · evidence · ownership** leak across the bank → capture intent → map resolution leakage → prioritise the mission (pain × economics × feasibility) → launch a governed Customer Resolution Mission → prove ROI & scale. banking-os.md itself flags this as *"a close cousin of the internal APA Domain Matrix value-bleed method."*
- The **APA Domain Matrix** (`knowledge/domains/apa-matrix/`) operationalises exactly this with a concrete catalog: 4 LOBs × 9 domains × **65 process simulations**, an L1 automation-potential heatmap (HIGH/MED/LOW), and a per-process **Value Bleed (desirability) → Banking OS Process Simulation (feasibility) → Elastic Operations Business Case (viability)** engine. Value Bleed = the resolution-loop's "map resolution leakage" step, sized in $; the 6-layer simulation = the governed future-state (Sentinel/NEXUS/Intelligence Fabric/Grand Central); the Elastic Ops business case = "prove ROI & scale".

**Relationship verdict:** the APA matrix is the **canonical, data-backed instantiation** of the resolution-loop value-leakage method — not a duplicate to reconcile away. The §9 method is the *principle*; the APA matrix is the *catalog + per-process engine* that executes it. The drift to fix is **upstream**: the generic value methodologies (`value_lever_framework.md`, `capability_driven_patterns.md`) still use the lifecycle flywheel and Problem-Type taxonomy and **do not yet point at either §9 or the APA matrix**. Cross-linking them — "for AI/agentic and operations value, use the resolution-loop method (banking-os.md §9) operationalised by the APA matrix" — unifies the value method across the tree. The matrix's $/% figures are illustrative reference values (its README says re-base on client data), so there is no fact conflict with the value pools; align by mapping the APA business-case outputs (Growth/Efficiency/Control) onto the three value pools.
